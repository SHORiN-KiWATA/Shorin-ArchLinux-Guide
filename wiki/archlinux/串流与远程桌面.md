# 串流与远程桌面

把一台电脑的画面和操作通过网络实时送到另一台设备上，就是本文的主题。按目标分两类：**串流**追求游戏的实时性，用 GPU 硬编码传高帧率画面，Moonlight、Parsec 是代表；**远程桌面**追求办公和运维的可用性，省带宽、能穿内网，RDP、VNC、RustDesk 是代表。打游戏用串流，办公用远程桌面，界限大抵如此。

跑服务端、被采集画面的一端叫**串流源**；跑客户端、看画面传操作的一端叫**客户端**。手机、平板、另一台电脑都能当客户端，躺在被窝里玩台式机的游戏就是它最经典的用法。

串流协议不关心两端的系统是什么：串流源可以是 Arch 本机、局域网里的另一台电脑，也可以是虚拟机里的 Windows——想借 Windows 的游戏兼容性又不想离开 Linux 桌面的时候，这一路很好用。

>串流和直播不是一回事：串流的观众是自己，直播的观众是平台。

## 串流

### 服务端：Sunshine

> [Sunshine](https://github.com/LizardByte/Sunshine) 是开源的串流服务端，本文的主线方案。

装在哪台机器上，哪台机器就是串流源：

- **Arch 本机**：

  ```bash
  yay -S sunshine
  ```

  >Sunshine 不在官方仓库。AUR 上 `sunshine` 是本地编译安装，`sunshine-bin` 直接装官方预编译的二进制，任选其一。

- **Windows**（常见形态：虚拟机里的 Win11）：官网下载安装包，一路下一步。

装好后启动，浏览器打开 Web 网页（`https://localhost:47990`），设置账号密码并登录，服务端就绪。

>虚拟机作串流源的前提是虚拟机本身已经装好，见[安装 Win11 虚拟机](KVM虚拟机.md#安装-win11-虚拟机)。文件共享、显卡直通之类的虚拟机内容也都住在 [KVM虚拟机](KVM虚拟机.md)。

### 客户端：Moonlight

> [Moonlight](https://github.com/moonlight-stream/moonlight-qt) 是配合 Sunshine 的开源客户端，各平台都有。

- Arch 本机：

  ```bash
  sudo pacman -S moonlight-qt
  ```

- 手机、平板：应用商店搜 Moonlight。

打开客户端，同一局域网内它会自动搜索到 Sunshine，点击连接会给出 PIN 码，回到服务端的 Web 网页输入 PIN，配对完成。之后在客户端点图标就开始串流了。

### 替代方案：Parsec

[Parsec](https://parsec.app/) 把服务端和客户端打包成了一个软件：两边装好、登录同一个账号就能用，配置最简单。缺点是账号捏在 Parsec 手里，可调的画质参数少，Linux 端也只有 AUR 里的 `parsec-bin`。

### 串流源的显示器问题

服务端采集的是某台显示器上的画面。串流源上没有插显示器——无头主机、合盖的笔记本、虚拟机——就没有画面可采，更没法自定义串流的分辨率。解法按串流源的系统选：

- 源是 **Windows**（比如 Win11 虚拟机）：装 [Virtual-Display-Driver](https://github.com/VirtualDrivers/Virtual-Display-Driver)（下称 VDD），给系统凭空加一台分辨率随便设的显示器。

- 源是 **Linux**：没有 VDD 可装，也不需要——内核原生就能伪造一台，就是下一节的虚拟显示器，而且效果更好。

- 源上插着真显示器：不装任何东西也能串，但分辨率被真显示器绑死；想自定义串流分辨率，下面的虚拟显示器同样适用。

## 虚拟显示器（免硬件诱骗器）

显卡只有检测到接口上插了显示器，才会真正输出画面。以往想无中生有，要么插一个几十块钱的“显卡欺骗插头”（也叫诱骗器、Dummy Plug），要么需要特定的桌面环境提供特定虚拟桌面功能。本节介绍第三种方式：什么都不插，让内核伪造显示器的 EDID 数据，凭空“骗”出一台虚拟显示器。

>前提：显卡上有多个显示接口，且显卡本身支持多屏渲染，主流显卡都满足。

>实测场景：Sunshine 串流主机，稳定可用。无头服务器、远程桌面等其他场景同理。

### 和 Virtual-Display-Driver 的关系

上一节说过，Windows 源的解法是 VDD。它和本节的虚拟显示器做的是同一件事：显卡没接真显示器时，伪造一台出来，让系统有画面可渲染、可采集，串流才有内容可传。

不过实现思路上，VDD 走的是“添加虚拟显卡”这条路线：它往 Windows 里加了一块虚拟显卡，虚拟显示器挂在这张卡上，渲染发生在虚拟显卡，画面最后还要拷贝回真正干活的显卡去编码输出。Linux 上也有同形的做法，比如给系统添加一块带显示输出的 vGPU，效果一样，但同样多一层内存拷贝。

本节的 EDID 则绕开了这条弯路：不添加任何设备，直接让真显卡自己的接口“假装”插了显示器，渲染、采集、编码都发生在同一张显卡上，没有额外拷贝。

所以 Windows 源用 VDD，Linux 源用本节的方法，各管各的系统，互不冲突。

### 原理

一共三件事：

1. **`drm.edid_firmware=<接口>:<文件>`**：告诉内核，指定接口（如 `DP-1`）不要去探测显示器，直接使用我们提供的 EDID 数据。

2. **`video=<接口>:e`**：强制将该接口置为启用状态，忽略物理连接检测。没有它，内核即使拿到了 EDID，也不会认为接口处于已连接状态。

3. **打包进 initramfs**：显卡驱动在系统启动非常靠前的阶段加载，那时根文件系统还没挂载，所以 EDID 固件必须先放进 initramfs。

>EDID 是显示器插上后向显卡“自我介绍”的一小块数据：厂商、型号、支持哪些分辨率和刷新率都在里面。伪造一块，显卡就“看见”了一台不存在的显示器。

### 配置步骤

#### 确认显卡接口名称

```bash
ls -d /sys/class/drm/card*-*
```

常见输出如 `card0-DP-1`、`card0-HDMI-A-1`，`-` 后面的部分就是接口名。挑一个空闲接口（对应 `status` 文件内容为 `disconnected` 的），下文都以 `DP-1` 为例。

#### 准备 EDID 固件

>以前内核自带 `edid/1920x1080.bin` 之类的现成固件可以直接引用，6.9 起已经移除，所以现在都需要自己准备文件。

EDID 本质上就是一小段“显示器自我介绍”的二进制数据，内容完全可以定制：厂商型号随便填，分辨率刷新率想写哪个写哪个，网上到处能找到现成的。我们只提供了一个还不错的版本：本仓库的 [files/edid.bin](../files/edid.bin)，一台 4K@60Hz 显示器的完整 EDID，下载它然后放到固件目录就行：

```bash
sudo mkdir -p /usr/lib/firmware/edid
sudo cp 下载路径/edid.bin /usr/lib/firmware/edid/edid.bin
```

想虚拟出自己的真显示器的话，也可以直接提取它的 EDID，分辨率、刷新率都是现成的：

```bash
sudo cat /sys/class/drm/card0-DP-1/edid | sudo tee /usr/lib/firmware/edid/edid.bin > /dev/null
```

>要在显示器实际插着的时候提取，提取出来的文件非空才算成功。

#### 打包进 initramfs

编辑 `/etc/mkinitcpio.conf`，把 EDID 文件加进 `FILES=()`：

```bash
FILES=(/usr/lib/firmware/edid/edid.bin)
```

重新生成 initramfs：

```bash
sudo mkinitcpio -P
```

#### 内核启动参数

编辑 `/etc/default/grub`，在 `GRUB_CMDLINE_LINUX_DEFAULT` 中添加：

```text
drm.edid_firmware=DP-1:edid/edid.bin video=DP-1:e
```

>冒号前面是接口名，后面是固件路径。注意这里写的是相对 `/usr/lib/firmware/` 的路径，所以是 `edid/edid.bin`。

>接口名按第一步的实际输出替换，HDMI 一般是 `HDMI-A-1`。

>用 systemd-boot 的话，把参数追加到启动项的 `options` 行里即可。

更新 GRUB 配置：

```bash
sudo grub-mkconfig -o /boot/grub/grub.cfg
```

#### 重启验证

重启后逐项检查：

```bash
# 1. 确认内核参数生效
cat /proc/cmdline

# 2. 接口状态应该变成 connected
cat /sys/class/drm/card0-DP-1/status

# 3. 应该能列出虚拟显示器的分辨率
cat /sys/class/drm/card0-DP-1/modes
```

看到 `connected` 和分辨率列表就成功了。之后在桌面环境的显示器设置里会多出一台“插着”的显示器，串流或远程桌面时让画面输出到它就可以了。

## 远程桌面

和串流相反，远程桌面不追求帧率，追求省带宽和穿透内网，把办公桌面稳定地送过去，代价是打游戏普遍不行。这个领域在 Linux 上好用的方案不多，下面直接给经过验证的组合，其余的只列名字。如果只记一条，就记 RDP 这条线：双向都好用，Windows 和 Linux 互连都能稳稳覆盖。

### 在 Windows 上操作 Linux

GNOME 用户有官方答案：**设置 → 系统 → 远程桌面**。这是 GNOME 内置的 RDP 服务端（gnome-remote-desktop），不是一个单独的应用，开关就在设置里。它有两种模式：**桌面共享**，把当前登录的会话共享出去；**远程登录**（GNOME 46 起），机器没人用时也能连进去开一个新会话，显示器甚至可以在远程那一头配置，headless 场景正好用上。Windows 这边什么都不用装，系统自带的“远程桌面连接”（mstsc）填上 IP 直连，体验很好。

### 在 Linux 上操作 Windows

体验很好的是 [RustDesk](https://rustdesk.com/)：开源远控，两端装好、输 ID 和密码就能连，还可以自建中继服务器。

用 RDP 的话，FreeRDP 的 SDL 版 `sdl-freerdp` 是目前不绑定桌面环境的最佳方案，只有一条代价：没有图形界面，全靠命令行参数配置。它对端不挑食，连 Windows 和连 Linux 的 RDP 桌面都一样好使。

>Windows 侧要提前在“设置 > 系统 > 远程桌面”里打开允许远程连接。

### 其余的名词

xrdp、VNC（TigerVNC）、KRfb、TeamViewer、AnyDesk、向日葵、ToDesk，名字列在这里，需要时自行了解。

### SPICE

你平时在 virt-manager 里打开虚拟机窗口，画面就是靠 SPICE 协议传的，详见 [KVM虚拟机](KVM虚拟机.md)。它服务的是虚拟机，和上面讲的串流、远程桌面不是一个东西，名词认识一下即可。

值得注意的区别是：RDP 这类协议自带“虚拟显示器”——会话是凭空创建的，连上去就有一块屏幕，所以被连的机器没有显示器也照样能用，GNOME 的远程登录、xrdp、Windows 自带的远程桌面都是这个原理。VNC 要看用法：Xvnc 这种虚拟桌面模式和 RDP 一样无中生有；“镜像现有屏幕”的用法才需要有屏幕存在，Wayland 下没有屏幕时就轮到上一节的 EDID 虚拟显示器出场了。

而串流不一样：Sunshine 采集的是显卡上真实存在的显示器输出，没有任何虚拟会话可以指望。这就是为什么串流的无显示器问题必须靠 EDID 来解决。
